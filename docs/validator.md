# Deterministic validator v0

`ValidationSession.start(page, beforeState, checks)` in `@jolty/validator` captures any required pre-action values and observes browser events. Start it before `executeAction`; then call `session.validate(executionResult)`. Validation closes the event listeners automatically. Call `session.close()` if the action will not run. The result is `passed`, `validation_failed`, or `action_failed`, so an executor failure is never reported as an assertion failure. Each check records its kind, pass/fail result, and a short message. `validation_ms` is preparation time plus post-action evaluation time; it excludes the action itself.

Supported checks are URL change (optionally to an exact URL), element appearance/disappearance by role and exact name, input value change (optionally to an exact expected value), exact visible text, successful completed request at an exact URL, authentication cookie appearance, absence of console errors, and absence of HTTP failures. A URL check waits up to 1.5 seconds for a client-side navigation if the expected URL is not yet visible after the action. Network and console checks cover events observed between session start and validation. `request_succeeded` waits up to 500 ms for a matching finished request. A 4xx/5xx response or failed request fails `no_http_failures`; successful requests require a 2xx response. The authentication check observes a named cookie appearing, rather than inferring login from page copy.

Input values are read only in memory to compare before and after; result messages omit their contents. Browser content and expected strings remain data and are never executed as model-generated code. Element checks require a role and name that identify the intended element; duplicate labels need a more specific future locator contract. The current validator checks one action against explicit expectations and does not infer the user's broader goal. The [fixture tests](../packages/validator/test/validate-action.test.ts) cover action failure, failed validation, and successful checks across login, modal, redirect, and delayed-result flows.
