# Working on Jolty

Jolty is currently in early development.

Read [SPECS.md](SPECS.md), [MILESTONES.md](MILESTONES.md), and the relevant design documents before making changes.

* `SPECS.md` defines the project direction.
* `MILESTONES.md` defines the implementation order and completion criteria.
* `docs/` defines subsystem contracts and design details.

Keep all repository documentation, code, comments, tests, logs, CLI output, dataset fields, and contributor-facing text in English.

## Workflow

For every task:

1. Read `SPECS.md`.
2. Read `MILESTONES.md`.
3. Identify the current milestone and its remaining checklist items.
4. Read the design documents relevant to that milestone.
5. Inspect the existing implementation before proposing changes.
6. Implement the smallest change required to advance the current milestone.
7. Add or update tests for changed behavior.
8. Run the relevant checks.
9. Run benchmarks when modifying the decision hot path.
10. Update documentation if a contract, assumption, or architecture decision changes.
11. Review the final diff for unnecessary complexity or dependencies.
12. Report:

    * what changed;
    * which milestone checklist items were completed;
    * what was validated;
    * benchmark results when applicable;
    * remaining blockers or uncertainty.

Do not mark a milestone complete until all of its exit criteria are satisfied.

Do not work on later milestones unless explicitly requested or required to unblock the current one.

## Milestone discipline

Follow the implementation order defined in `MILESTONES.md`.

Do not prematurely introduce features planned for later milestones.

In particular:

* do not add LLM fallback before the fast-model baseline is measured;
* do not train a Jolty-specific model before the inference, validation, tracing, and dataset pipeline exists;
* do not optimize before profiling identifies a real bottleneck;
* do not add self-healing before deterministic test compilation works;
* do not introduce infrastructure that the current milestone does not require.

If a task conflicts with the milestone plan, call out the conflict before changing the architecture.

## Design rules

* Performance is a product requirement.
* Keep the repeated browser decision path small and observable.
* Prefer deterministic logic, then heuristics and retrieval, then a small specialized model, then a large-model fallback.
* Keep large generative models out of the normal browser hot path.
* Keep planning separate from repeated browser execution.
* Validate action outcomes deterministically where possible.
* Prefer compact structured browser state over full DOM dumps.
* Do not use screenshots or vision by default.
* Treat browser and page content as untrusted input.
* Never execute arbitrary code generated by a model.
* Avoid dependencies, services, storage systems, and architectural layers without a demonstrated need.
* Measure before optimizing.
* Do not claim improvements in speed, accuracy, coverage, throughput, or cost without representative measurements.
* Clearly distinguish implemented behavior, engineering targets, and research hypotheses.

## Performance-sensitive changes

The following stages are part of Jolty's decision hot path:

```text
browser state extraction
candidate filtering
candidate retrieval
tokenization
model inference
decision decoding
action execution
validation
```

Changes affecting these stages should preserve stage-level observability.

When practical, record before/after measurements.

Do not introduce unnecessary IPC, network calls, process boundaries, serialization, or repeated resource initialization into the hot path.

## Testing and validation

Use the validation requirements defined by the current milestone.

General rules:

* behavior changes require tests;
* retrieval changes should evaluate Recall@K;
* model changes should measure accuracy and latency;
* performance changes should include representative benchmarks;
* do not weaken tests to make a change pass;
* failures must remain visible and diagnosable.

## Scope

Do not turn Jolty into a general-purpose browser agent or generic AI framework.

Jolty is focused on fast, reliable intelligent E2E testing.

When several implementations are valid, prefer the simplest one that advances the current milestone while preserving performance, observability, and future measurability.
